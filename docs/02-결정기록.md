# 기술 결정 기록

> **왜 이 문서가 있나**: 면접에서 "이건 왜 이렇게 하셨어요?"에 답하려면 결정과 이유가 남아 있어야 한다.
> 이해 못 한 채 쌓인 결정은 전부 부채가 된다.
>
> **작업 규칙**: 모든 기술 선택은 **이유를 먼저 설명하고 승인을 받은 뒤** 채택한다.

## D-01. 앱이 아니라 웹으로 만든다 ✅

**결정**: React 19 + TypeScript + Vite + Tailwind + Recharts 웹 애플리케이션

**이유**
1. **사용자가 운영자다.** 하루 종일 스프레드시트를 보는 사람이 A/B 회귀 비교표를 나란히 놓고 본다. 모바일에서 볼 물건이 아니다
2. **실무 현실이 그렇다.** 사내 운영 도구·어드민이 앱인 경우는 거의 없다. 앱으로 만들면 실무 감각 부재로 읽힌다
3. **채용담당자가 APK를 설치하지 않는다.** 링크 하나로 열려야 한다
4. plc-dashboard·서울시 핫스팟에서 쓰던 스택 그대로 → **새로 배울 것이 없어야 마감(2026-08-26) 안에 끝난다**

## D-02. 채점은 룰 기반 주력, LLM 판정은 보조 ✅

**결정**: 회귀 판정(좋아졌나/나빠졌나)은 **룰 기반 지표로만** 한다. LLM 점수는 화면에 표시만 하고 비교에는 쓰지 않는다.

**이유 — 결정성(determinism)**

detekt를 CI에 걸어 배포를 막을 수 있는 이유는 "같은 입력에 항상 같은 결과"이기 때문이다. 어제 통과, 오늘 실패면 아무도 안 믿는다.

**LLM에는 이 성질이 없다.** 같은 질문·답변을 두 번 채점시키면 4점, 3점이 나온다.

그래서 이런 상황이 생긴다:
> 모델을 A→B로 올렸더니 평균이 3.8 → 4.1이 됐다.
> **모델이 좋아진 건가, 채점기가 흔들린 건가?**

LLM 판정만 쓰면 구분할 방법이 없다. 공고 담당업무에 *"AI 모델 업데이트 시 AI 답변 검증"* 이 있는데, 회귀 비교가 성립하지 않으면 도구의 존재 이유가 사라진다.

| | 룰 기반 | LLM 판정 |
|---|---|---|
| 결정성 | **있음** | 없음 |
| 비용 | 0원 | 호출당 과금 |
| 잡는 것 | 숫자 팩트, 인용 유무, 금지어, 거절 여부 | 자연스러움, 완결성, 실제로 답했는지 |

**부수 효과**: Gemini 무료 티어 한도 안에서 충분히 돌아간다.
**한계**: `temperature=0`으로 LLM 흔들림을 줄일 수는 있으나 없애지는 못한다. 그래서 "줄인다"가 아니라 **"회귀 판정에서 배제한다"**.

## D-03. 채점의 정답은 골든셋에 사람이 직접 붙인다 ✅

**결정**: 골든셋 **60문항** 각각에 **기대 정답 + 근거 출처 + 기준일**을 사람이 확인해 기록한다. 채점 시 우리 RAG 검색 결과를 정답으로 삼지 않는다.

**이유**

우리 도구의 목적은 **카뱅 AI의 답을 채점하는 것**이지 카뱅의 RAG를 재현하는 것이 아니다.

만약 우리 검색이 엉뚱한 문서를 찾아와 "오답" 판정이 났다면 — **카뱅 AI가 틀린 건가, 우리 검색이 틀린 건가?** 구분이 안 된다. D-02와 같은 문제다. **채점기 자체가 흔들리면 안 된다.**

**기각한 대안**: 크롤링한 문서로 RAG를 만들어 자동으로 정답을 뽑는 방식 → 채점기의 결정성이 깨진다.

## D-04. 벡터 검색에 pgvector(Supabase)를 쓴다 ✅ ※ 번복된 결정

**최초 판단(기각됨)**: 문서가 20건 규모이므로 메모리 배열 코사인 유사도로 충분. 벡터 DB는 오버엔지니어링.

**번복 이유 — 오버엔지니어링을 줄이면 만나야 할 문제를 못 만난다**

메모리 배열은 매번 새로 임베딩하므로 **항상 최신 문서로 검색된다.** 그런데 벡터 DB를 쓰면 이 문제가 생긴다:

> 문서를 고쳤는데 **인덱스에 옛날 벡터가 남아 있다.**
> 새 문서를 썼는데 AI는 여전히 옛날 답을 한다. 원인을 한참 못 찾는다.

이것이 실제 RAG 운영의 대표적 고통이고, **카뱅 팀이 "RAG 문서 관리"라고 부르는 업무의 핵심**이다. 메모리 배열로 하면 이 문제를 아예 안 겪는다.

**추가 이득**: pgvector는 Postgres 확장이므로 **벡터 검색이 SQL 쿼리가 된다.**
공고 우대사항 *"SQL, Python 등을 활용한 데이터 분석"* 과 직접 연결된다.

**Supabase를 고른 이유**: Postgres 기반이라 pgvector를 쓸 수 있고, 학교 청소 외주에서 이미 써봤다.

**리스크와 대응**: 무료 티어는 1주일 비활동 시 프로젝트 일시정지 → **GitHub Actions cron으로 주기적 핑**을 보내 유지한다.

**판단 기준 (일반화)**
> 기술 자체가 자랑거리가 아니라, **그 기술을 써야만 만날 수 있는 문제를 만나기 위해** 넣는다.

## D-05. 키워드 검색과 임베딩 검색을 둘 다 만들고 비교한다 ✅

**결정**: 두 방식을 모두 구현하고 **문서 형식에 따른 적중률 차이를 측정**한다.

**이유**

하나만 만들면 실험이 성립하지 않는다. 둘을 비교해야 이런 발견이 나온다:
> *"문서 제목을 질문형으로 바꿨더니 임베딩 검색 적중률은 올랐는데 키워드 검색은 그대로였다."*

이것이 *"RAG 문서 생성 및 관리"* 업무의 실제 노하우다. 실무 RAG도 둘을 섞어 쓴다(하이브리드 검색).

| | 키워드 검색 | 임베딩 검색 |
|---|---|---|
| 방식 | 질문의 단어가 문서에 있으면 매칭 | 문장을 벡터로 바꿔 의미 유사도 |
| "돈 모으기"로 "회비" 문서 찾기 | **못 찾음** | 찾음 |
| 속도·비용 | 빠름, 무료 | 느림, API 비용 |

## D-06. 백엔드 서버를 만들지 않는다 ✅

**결정**: 채점은 **로컬 Node/Python 배치**로 실행해 `results.json`을 생성하고, 웹은 그 JSON만 읽어 표시한다.

```
[로컬 배치]  문서 임베딩 → pgvector 저장 → SQL 벡터 검색 → 채점(룰+LLM)
                                    ↓
                            results.json → 레포 커밋
                                    ↓
[웹 대시보드]  JSON 읽어서 표·차트로 표시   ← 절대 안 죽음
```

**이유**
1. **백엔드가 할 일이 없다.** 채점은 60문항을 한 번에 도는 **배치 작업**이지 실시간 요청이 아니다
2. **링크가 죽으면 프로젝트가 죽는다.** 무료 백엔드는 비활동 시 슬립. 채용담당자가 링크를 눌렀는데 30초 로딩되면 그냥 닫는다
3. **API 키가 브라우저에 노출되지 않는다.** 로컬에서만 키를 쓴다
4. **인프라에 2~3일이 간다.** 그 시간은 310스텝 관측에 들어가야 한다. 데이터가 없으면 도구는 빈 껍데기다

**pgvector와의 관계**: 벡터 검색은 **로컬 배치 단계에서만** Supabase에 붙는다. 웹 대시보드는 Supabase에 의존하지 않으므로, 프로젝트가 일시정지돼도 리포트는 살아 있다.

**기각한 대안 — Django**

*"Django를 넣어서 새로 만나는 문제가 무엇인가?"* 인증·ORM·배포는 전부 **웹 개발 문제이지 대화형 AI 운영 문제가 아니다.** 그 팀의 고통 목록에 없다.
- Python 우대사항 → 채점 스크립트와 데이터 분석을 Python으로 쓰면 이미 충족
- SQL 우대사항 → pgvector 쿼리로 충족
- Supabase가 이미 DB·API 역할을 한다. Django를 얹으면 같은 걸 두 번 만드는 것

**한계 인정**: 백엔드가 있으면 웹에서 버튼을 눌러 재채점을 돌릴 수 있고, 데모로는 더 낫다. 링크 생존과 개발 시간을 대가로 내준 선택이다.

## D-07. 문서는 카뱅 공개 문서를 **수동 열람**으로 수집한다 (크롤링 안 함) ✅

**결정**: 근거 문서는 카카오뱅크 공개 문서 20~30건. **자동 크롤링하지 않고** 브라우저로 직접 열람해 참고한다. **원문은 저장소에 커밋하지 않는다.**

### 왜 카뱅 문서인가 (다른 주제가 아니라)

**발견과 해결이 같은 대상이어야 이야기가 안 쪼개진다.**

> 카뱅 AI가 이 질문에 못 답했다 → 이 영역 문서가 없더라 → 문서를 써 넣었다 → 이제 답한다 → 그런데 다른 3개가 망가졌다

한 줄기로 흐른다. 다른 주제(학사규정·통신요금 등)로 하면 *"관측"* 과 *"실험"* 이 따로 놀고, 면접에서 "그 실험이 카뱅과 무슨 상관이죠?"에 답이 궁색해진다.

**금융 문서가 실험 재료로 좋은 이유**: 숫자가 많아 룰 기반 팩트체크가 실제로 작동하고 / 조건이 복잡해 부분 정답 판정이 의미를 갖고 / 비슷한 상품이 여럿이라 검색 혼동이 자연스럽게 생기고 / 긴 약관과 짧은 FAQ가 공존해 "쪼갠 문서 vs 통짜 약관" 비교가 그냥 된다.

### 왜 크롤링을 안 하는가

`robots.txt` 확인 결과 검색엔진 4개(Googlebot·Yeti·Daum·facebookexternalhit)만 허용하고 **`User-agent: *` 는 전면 차단**이다. 자체 크롤러는 명시적으로 거부된 상태.

**이건 기술 문제가 아니라 평판 문제다.** 지원하는 회사가 명시적으로 거부한 방식으로 데이터를 긁어서 그걸 지원서에 링크로 낸다 — 면접에서 *"robots.txt는 확인하셨어요?"* 한 마디면 끝난다. 은행이라 더 그렇다.

**기술적으로 가능한 것과 해도 되는 것은 다르다.**

리포트에 이 사실을 명시한다. 확인했다는 것 자체가 증거이며, "꼼꼼함"을 말로 주장하는 것보다 강하다.

### 잃는 것이 없음을 확인

크롤링의 유일한 이점은 **문서 변경 감지 → 재인덱싱 실험**(D-04의 근거)이었으나, 이는 **금리가 바뀌었다고 가정하고 문서를 직접 수정**하면 그대로 성립한다. 오히려 실제 변동을 기다릴 필요 없는 **통제된 실험**이 된다.

## D-08. LangChain · LangGraph를 쓰지 않는다 ✅

**결정**: RAG 파이프라인을 직접 구현한다. 프레임워크를 얹지 않는다.

**이유** — D-04(pgvector 채택)와 **같은 기준**을 적용하면 정반대 결론이 나온다.

> 기술 자체가 자랑거리가 아니라, **그 기술을 써야만 만날 수 있는 문제를 만나기 위해** 넣는다.

- **pgvector** → 인덱스 동기화 문제를 **만나게 해준다** → 넣는다
- **LangChain** → 내부에서 무슨 일이 일어나는지 **가려버린다** → 뺀다

LLM·RAG를 처음 다루는 상황에서 두꺼운 추상화를 얹으면 돌아가긴 하는데 **왜 돌아가는지 모른 채로** 간다. 이 프로젝트의 목적 하나(경험 공백 메우기)가 통째로 사라진다.

**직접 구현의 전부**
```
① 문서 → 임베딩 API → 벡터                                    5줄
② pgvector 테이블에 INSERT                                     SQL 1줄
③ 질문 임베딩 → SELECT ... ORDER BY embedding <=> $1 LIMIT 5   SQL 1줄
④ 찾은 문서를 프롬프트에 넣어 LLM 호출                          10줄
```
합쳐 100줄 안쪽. **프레임워크를 배우는 시간이 직접 짜는 시간보다 길다.**
그리고 ③의 `<=>`(pgvector 거리 연산자)를 직접 써보는 것이 우대사항의 "SQL 활용"인데, LangChain을 쓰면 이 줄을 영영 못 본다.

**LangGraph**는 에이전트의 상태 흐름을 그래프로 구성하는 도구다. 이 프로젝트는 에이전트가 아니라 **일방향 배치 채점 파이프라인**이라 쓸 자리가 없다.

**과장하지 않기**: 면접관이 LangChain 사용 여부를 볼 가능성은 낮다. 개발직이 아니다. 그리고 **LangChain을 썼다고 감점되지도 않는다** — 실무에서 흔히 쓴다. 안 쓰는 이유는 "면접에 불리해서"가 아니라 **"이해까지 가려면 직접 짜는 게 빠르고, 그 100줄이 곧 이해라서"** 다.

## D-09. 관측은 전 영역, RAG 실험은 통장/저축 한 곳 ✅

**결정**: 골든셋 관측은 6개 카테고리(대출·통장저축·카드·외환·투자·인증보안)에 걸쳐 넓게. **RAG 문서 실험은 통장/저축으로 좁힌다.**

**이유 — 두 작업이 필요로 하는 것이 다르다**

| | 필요한 것 | 넓힐 수 있나 |
|---|---|---|
| **관측** (카뱅 AI에게 묻고 채점) | 문항 + 기대 정답. **답은 카뱅 AI가 한다** | ✅ 넓게 가능 |
| **RAG 실험** (내가 문서 쓰고 검색) | **문서를 내가 다 써야 한다** | ❌ 6개 영역에 흩으면 영역당 3~5건, 실험 불성립 |

**왜 대출(809개, 1위)이 아니라 통장/저축(506개, 2위)인가**

> 대출 답변은 대부분 *"개인 심사에 따라 다릅니다"* 다. 한도도 금리도 승인 여부도.
> **문서를 아무리 잘 써도 해결되지 않는다.** RAG 문서 실험 대상으로 부적합하다.
>
> 통장/저축은 **사실 기반**이다. 금리 몇 %, 한도 얼마, 몇 개까지, 어떻게 해지.
> 문서로 답이 되는 영역이라 **문서를 고치면 답이 바뀌는 것이 측정된다.**
> 그리고 "박스" 계열 6종·적금 5종의 **검색 혼동이 여기 집중**돼 있다.

**서사**: *"전 영역을 관측해 어디가 약한지 지도를 그렸습니다. 전부 메울 수는 없으니 한 영역을 골라 문서를 써넣고 개선을 측정했습니다."*
→ 갭을 찾고 → 우선순위를 정하고 → 하나부터 메운다. **어시스턴트가 하게 될 일 그 자체다.**
→ *"통장/저축만 했습니다"* 보다 *"지도를 그리고 그중 하나를 골랐습니다"* 가 강하다. 선택에 근거가 있으므로.

## D-11. 추천 질문 경로은 **항상 첫 번째 추천**만 따라간다 ✅

> 원래 `docs/03` 절대규칙 #1에 *"선택이 매번 달라지면 재현성 측정이 불가능해진다"* 한 줄로만 있었다.
> **면접 질문이 될 만한 결정인데 근거가 얇아서** 기각 대안까지 갖춰 여기로 승격한다 (2026-08-17).

### 핵심은 "왜 첫 번째냐"가 아니라 **"왜 고정이냐"**

추천 질문 경로은 **분기 그래프**다. 매 턴 3개씩 갈라지면 5턴에 3⁵ = **243경로**, 시드 22개면 5,000경로가 넘는다.
질문 한도는 **3시간당 90회**. 전수 탐색은 애초에 선택지가 아니다.
→ 어떤 형태로든 **가지치기 규칙**이 필요했고, 문제는 *어떤 규칙이 데이터를 안 망가뜨리는가* 였다.

| 대안 | 기각 이유 |
|---|---|
| 관측자가 흥미로운 것을 고른다 | **관측자의 취향을 측정하게 된다.** 22개 시드를 서로 비교할 근거가 사라진다 |
| 매번 무작위로 고른다 | 2라운드에서 경로가 달라졌을 때 **AI 때문인지 주사위 때문인지 구분 불가.** 재현성 측정 자체가 성립 안 함 |
| 모든 가지를 전부 탐색 | 위 계산대로 한도 초과. 애초에 불가능 |
| **첫 번째로 고정** ✅ | **결정적이고 재현 가능하다.** 그리고 추천이 1개라도 있으면 항상 정의된다 (아래) |

### 왜 하필 첫 번째인가 (마지막이나 세 번째가 아니라)

> ⚠️ **처음에 쓴 근거를 철회한다 (2026-08-17).**
> *"첫 번째는 서비스가 가장 밀어주는 것"* 이라고 썼는데 **그건 우리가 알 수 없다.**
> 순서가 관련도 순인지, LLM 생성 순서 그대로인지, 무작위인지 랭킹 로직은 카뱅 내부에 있다.
> 근거 없이 의미를 부여했다 → 폐기. `## ⚠️ 폐기 항목`에 준하는 자기수정으로 남긴다.

남는 이유는 하나뿐이고, 그것으로 충분하다 —
**첫 번째는 추천이 존재하기만 하면 반드시 존재하는 유일한 위치다.**

추천 개수는 고정이 아니다. 지금은 3개지만 2개나 5개가 뜰 수 있다.

| 후보 규칙 | 개수가 바뀌면 |
|---|---|
| `마지막 것` | 매번 다른 깊이를 찍는 규칙이 된다 (3개일 땐 3번, 2개일 땐 2번) |
| `세 번째` | 2개만 뜬 턴에서 **규칙이 정의되지 않는다** |
| **`첫 번째`** ✅ | 추천이 1개라도 있으면 **항상 정의된다** |

110스텝을 끝까지 굴리려면 **한 번도 예외가 생기지 않는 규칙**이어야 한다. 첫 번째만 그 조건을 만족한다.
덤으로 **세는 행위가 없어 관측자 오류가 가장 적다** — 오타 하나가 90회 한도 하나를 먹는 조건에서 실질적인 이유다.

### 그래서 리포트는 순서에 의미를 부여하지 않는다

| 이렇게 쓰지 않는다 | 이렇게 쓴다 |
|---|---|
| *"첫 번째 추천은 서비스가 가장 밀어주는 경로다"* | *"추천 순서의 의미는 외부에서 알 수 없으므로, **임의로 고정한 한 경로**만 관측했다"* |

**의미를 주장하지 않으면 반박당할 곳도 없다.** 방어 가능한 쪽이 더 강한 문장이다.

### 🔴 이 규칙의 한계 — 리포트에 반드시 쓴다

우리가 측정한 것은 **"기본 경로의 도달률"** 이지 **"실제 도달률"이 아니다.**

실증 사례 (2026-08-17):

**① S03 4턴** — 추천 3번이 `대출 이자 계산기로 내 조건 넣고 월 이자 계산해줘` 였다.
**AI 금융계산기로 넘어갈 수 있던 유일한 분기**였는데 규칙상 1번으로 갔다.
→ 이 규칙 아래에서는 *"다른 AI 기능으로 넘어간 적 0회"* 라는 결론이 나오는데,
**그건 사실이 아니라 우리 표집 방식의 결과일 수 있다.**

**② S12 — 비교 질문에서 한쪽만 관측된다 (더 심각한 사례)**
시드가 `세이프박스랑 저금통 뭐가 달라?` 였고 AI는 **두 상품을 표로 정확히 대조**했다.
그런데 1턴 추천이 이랬다:

| 추천 | 어느 쪽 |
|---|---|
| 1. 세이프박스 보관한도 1억으로 올리는 방법 | **세이프박스** ← 규칙상 여기로 |
| 2. 저금통 동전 모으기랑 자동 모으기 뭐가 더 잘 모여? | 저금통 |
| 3. 저금통에서 부분 출금이 되는 경우가 언제야? | 저금통 |

→ **5턴 내내 세이프박스만 팠고 저금통은 1턴 이후 관측되지 않았다.**
비교 시드(S12·S13·S14)는 구조적으로 **한쪽으로 쏠린다.**
→ 2라운드에서 이 시드들은 **2번 추천으로 가는 회차**를 반드시 넣는다.

**③ S12 3턴 추천 3번 `세이프박스랑 MMF박스는 뭐가 달라?`**
AI가 스스로 혼동 축(보관 용기 6종)의 다른 상품으로 연결하려 했는데 규칙상 못 갔다.
**우리가 설계한 실험을 AI가 먼저 제안했는데 우리 규칙이 막았다.** 2라운드 최우선 후보.

→ 그래서 **2라운드가 보정 장치**다. 1라운드는 **폭**(결정적·전 시드), 2라운드는 **깊이**(신호 있는 시드만 다른 가지도).
이 한계는 리포트 「이 도구가 못 잡는 것」에 그대로 싣는다.

## D-12. 웹 대시보드는 Vite + React + TypeScript, 의존성 5개로 만든다 ✅

> CLAUDE.md 스택 줄에 적혀 있던 **Tailwind와 Recharts를 뺀다.** 스택 축소이므로 결정으로 승격한다 (2026-08-19).

**결정**: `react` · `react-dom` · `vite` · `@vitejs/plugin-react` · `typescript` **5개가 전부다.**
스타일은 CSS 파일 하나, 차트는 인라인 `<svg>`, 화면 전환은 `useState` 탭.

### 판단 기준은 D-04·D-08과 같은 것을 쓴다

> 기술 자체가 자랑거리가 아니라, **그 기술을 써야만 만날 수 있는 문제를 만나기 위해** 넣는다.

이 웹앱은 **고정된 JSON 한 덩어리를 표와 그림으로 바꾸는 일**이다.
여기서 만나야 할 문제는 *"관측 데이터를 어떻게 읽히게 만드는가"* 이지 프론트엔드 문제가 아니다.
그리고 **공고는 프론트엔드 직무가 아니다** — 담당업무는 데이터 모니터링·답변 검증·추천 질문 운영·RAG 문서 관리이고,
우대사항은 SQL·Python이다. 프론트에 쓰는 시간은 전부 관측·리포트에서 빼오는 시간이다.

### 기각한 대안

| 대안 | 기각 이유 |
|---|---|
| **Next.js** | 값어치가 서버(RSC·Route Handler·ISR)에 있는데 **D-06에서 서버를 안 만들기로 이미 정했다.** `output: 'export'`를 켜면 남는 건 파일 기반 라우터 하나인데 화면이 3~4개라 그것도 필요 없다. **쓰지 않을 기능의 설정 파일을 떠안는 선택** |
| **바닐라 JS · 단일 HTML** | 필터·정렬·선택 시드·펼친 턴이 동시에 도는 화면이다. 손으로 DOM을 갱신하면 **diff가 React보다 길어지고** 재렌더 버그는 원인 찾기가 가장 어려운 종류다. "가장 게으른 것"이 여기서는 React 쪽이다 |
| **Recharts** | 그려야 할 4종 중 **커버리지 히트맵과 추천 질문 경로 그래프를 Recharts로 못 그린다.** 절반을 SVG로 직접 쓸 거면 나머지 절반(막대·추이)도 `<rect>`·`<polyline>` 몇 줄이다. 라이브러리를 넣으면 **의존성은 늘고 코드는 안 줄어든다** |
| **Tailwind** | 대시보드 하나에 CSS 150줄이면 끝난다. 빌드 설정을 하나 더 얹을 규모가 아니다 |
| **라우터 · 상태관리 라이브러리** | 화면 3~4개에 `useState` 하나면 된다 |

### TypeScript는 남기는 이유

이 앱은 사실상 **`scored-round1.json`의 모양 그 자체**다. 유일하게 자주 날 실수가
`재탕.T1`을 `재탕.t1`로 쓰는 것인데 TS가 정확히 그것만 잡는다. 런타임 비용은 0이고 타입 파일도 하나면 된다.

### 배포는 Vercel 유지

GitHub Pages도 결과물이 같다(순수 정적이라 `vite build` 산출물이 그대로 올라간다).
**서비스 하나를 줄일 수 있다는 게 유일한 이점이었는데, 이미 Vercel을 쓰고 있어 계정 비용이 0이다.**
→ 이점이 사라졌으므로 CLAUDE.md에 적힌 Vercel을 그대로 둔다.

### 넣게 될 조건 — 미리 적어둔다

| 지금 뺀 것 | 넣을 조건 |
|---|---|
| 라우터 | 화면이 6개를 넘거나, **특정 시드 화면 URL을 공유**해야 할 때 |
| 차트 라이브러리 | 축·툴팁·반응형을 직접 쓴 코드가 **SVG 200줄을 넘길 때** |
| Edge Function (D-06 예외) | 방문자가 **자유 입력한 질문**으로 RAG 검색을 시연해야 할 때. 골든셋 60문항은 고정이라 **미리 계산해 JSON에 박으면 서버 없이 같은 체감**이 나온다 |

**한계 인정**: 이력서에 적히는 스택 이름이 짧아진다.
다만 이 프로젝트가 증명하려는 것은 프레임워크 숙련도가 아니라 **관측·채점·리포트**이고,
D-08(LangChain 기각)에서 이미 같은 기준으로 같은 대가를 치르기로 했다.

| 문서 형식에 따른 검색 적중률 차이 | 사내 툴·어드민 환경 |
| 하나 고치고 셋 망가지는 회귀 | |
| 커버리지 갭 우선순위 | |

**어시스턴트는 실무에서 코드를 거의 쓰지 않을 가능성이 높다** (인터뷰: 어드민 세팅, 콘텐츠 제작, 리스트업, 데이터 정리).
즉 **「도구를 직접 만든 것」 자체는 실무와 다른 일**이다. 그 차이가 강점이 되는 지점은 하나뿐이다 —
도구를 만들어본 사람은 **사내 툴이 무엇을 못 잡는지 알고**, *"이건 반복이니 자동화하면 되지 않을까요"* 를 말할 수 있다.

## 공감의 층위 — 리포트에서 지킬 태도

| | 무엇 | 이 프로젝트 |
|---|---|---|
| **겪어본 공감** | 실제로 같은 문제를 만나봄 | ✅ 인덱스 동기화 · 회귀 · 커버리지 갭 |
| **들어본 공감** | 그들이 말한 걸 읽고 이해함 | ✅ 공고 · 인터뷰 · 공개 자료 |
| 상상한 공감 | 그럴 것 같다고 추측 | ❌ 제일 약하고 티가 난다 |

> **"이건 겪어봤고, 이건 못 겪었습니다"를 구분해서 말할 수 있는 것 자체가 공감의 증거다.**
> 다 안다고 말하는 것이 오히려 공감 없음의 증거다.

→ 리포트에 **「이 도구가 못 잡는 것」** 과 **「제가 재현하지 못한 것」** 섹션을 반드시 넣는다.
